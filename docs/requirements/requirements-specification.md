## 1. Introduction

### 1.1 Purpose
HIVE is a modular honeypot network platform designed to collect, validate, normalize, store, and visualize security events generated by honeypots. The platform aims to help users observe suspicious activity, review security events, identify basic attack patterns, and investigate potentially malicious behavior through a centralized interface.

This document defines the functional requirements, non-functional requirements, user stories, acceptance criteria, verification procedures, and traceability relationships for HIVE. It serves as the primary requirements reference for implementation, testing, project planning, and evaluation.

### 1.2 Problem Statement
Honeypots can generate useful information about scanning, attempted exploitation, suspicious connections, and other potentially malicious activities. However, collecting and analyzing data from multiple honeypots can be difficult when each source produces different event formats or requires a separate monitoring interface.

HIVE aims to address this problem by providing a centralized platform that accepts events from supported honeypots, converts them into a common format, stores them, and presents relevant information through a dashboard.

The project will also explore basic detection rules, alert generation, access control, and security auditing. Its effectiveness will be evaluated through documented requirements and repeatable tests rather than unsupported claims about production readiness.

### 1.3 Objectives
The primary objectives are to:
1. Provide authentication for registered platform users.
2. Enforce role-based authorization on protected backend operations.
3. Register and manage supported honeypot sources.
4. Receive and validate security events from registered sources.
5. Normalize and store supported events in a common schema.
6. Evaluate configurable detection rules and generate alerts.
7. Provide authorized users with an interface for searching and reviewing events and alerts.
8. Record relevant administrative and security-related actions in audit logs.
9. Verify functional and non-functional requirements through automated and documented tests.
10. Provide reproducible setup and usage documentation.

### 1.4 Intended Audience
This document is intended for:
* Project team members responsible for implementation and testing.
* The project supervisor and course instructors.
* Reviewers evaluating the requirements, design, and verification process.
* Future developers extending the HIVE platform.

## 2. Project Scope

### 2.1 In Scope
The initial version of HIVE will include the following capabilities:
* A backend service implemented in Go.
* A REST API for supported platform operations.
* PostgreSQL for persistent storage.
* A React-based web interface.
* Authentication for registered users.
* Backend role-based authorization.
* Honeypot registration and management.
* Event ingestion and input validation.
* A common event schema for supported integrations.
* Persistent storage and retrieval of security events.
* Basic configurable detection rules and alert generation.
* Dashboard functionality for viewing and searching events and alerts.
* Audit logging for relevant security and administrative operations.
* Automated tests and a continuous integration workflow.
* Documentation covering setup, configuration, testing, and limitations.

SSH and HTTP/web honeypot integrations are intended initial integrations. Additional integrations will depend on implementation progress and feasibility.

The use of Elasticsearch, a simulated API honeypot, and other supporting components remains subject to the team's final architecture decisions.

### 2.2 Out of Scope
The following are excluded from the initial required scope:
* Replacing a production Security Information and Event Management (SIEM) or Security Operations Center (SOC) platform.
* Processing sensitive production data from hospitals, schools, or other organizations.
* Deploying unauthorized offensive infrastructure or conducting unauthorized attacks.
* Guaranteeing the detection of every attack or malicious activity.
* Supporting every possible honeypot protocol or event format.
* Claiming production-grade availability, scalability, or security without appropriate testing.
* Implementing complex machine-learning-based threat detection as a mandatory feature.
* Integrations that significantly delay completion of the core requirements.

### 2.3 Stretch Goals
The following features may be considered after the core requirements are satisfied:
* Additional honeypot integrations.
* Attacker fingerprinting and behavioral analysis.
* MITRE ATT&CK technique mapping.
* IOC extraction and threat intelligence export.
* Session replay or richer interaction analysis.
* Advanced detection rules.
* Additional visualization and reporting capabilities.

Stretch goals will not be considered mandatory acceptance criteria unless formally added to the approved requirements.

### 2.4 Assumptions and Constraints
The project assumes that:
1. Event sources can communicate with the HIVE backend through a supported interface.
2. The development environment can run the required software and database services.
3. The team can use synthetic or non-sensitive test data.
4. The initial deployment will be intended for academic demonstration and evaluation.
5. The system's security claims will be limited to properties demonstrated by its implementation and tests.

Constraints include the project deadline, team capacity, available computing resources, and the need to prioritize working core features over optional integrations.

## 4. System Overview and Architecture

### 4.1 Proposed Architecture
HIVE is designed around the following logical components:
1. **Honeypot and Event Sources:** Generate security-related events.
2. **Backend REST API:** Receives requests, validates input, and enforces applicable access controls.
3. **Event Processing Component:** Normalizes supported event formats and passes valid events for storage and analysis.
4. **Detection Component:** Evaluates configured rules and creates alerts when matching conditions are satisfied.
5. **PostgreSQL Database:** Stores users, roles or permissions, honeypot registrations, events, alerts, and audit records as required by the final schema.
6. **React Dashboard:** Allows authorized users to view and search available information.
7. **Testing and CI:** Runs automated checks against implemented requirements and relevant security controls.

Elasticsearch may be introduced if the team confirms that it is necessary for the selected event-search or analysis functionality. PostgreSQL remains the required persistent database for the initial architecture.

### 4.2 High-Level Data Flow
The intended event-processing flow is:
1. A supported honeypot generates an event.
2. The source submits the event through the supported API or integration.
3. The backend validates the request and required fields.
4. Valid events are converted into the common event schema.
5. The normalized event is stored.
6. The detection component evaluates applicable rules.
7. Matching rules create alerts.
8. Authorized users retrieve and review events and alerts through the dashboard.

The final implementation may use synchronous or asynchronous processing.

### 4.3 Actors

| Actor | Description |
| :--- | :--- |
| **System Administrator** | Manages platform configuration, users, roles, and honeypot registrations, subject to the implemented permissions. |
| **Security Analyst** | Reviews events and alerts and searches security information permitted by their role. |
| **Honeypot / Event Source** | Submits security events through a supported integration. |
| **Automated Test Runner** | Executes verification tests in the development or CI environment. *(Note: A verification participant rather than a human application user).* |

## 5. Functional Requirements
Functional requirements describe what the system must do. 
*Priority definitions:* **Must** (Required for initial deliverable), **Should** (Important, can be deferred if approved), **Could** (Optional enhancement).

### FR-01: User Authentication
* **Priority:** Must | **Related user story:** US-01
* **Description:** The system shall authenticate registered users before granting access to protected application functionality.
* **Verification:** Automated authentication tests.

### FR-02: Role-Based Authorization
* **Priority:** Must | **Related user story:** US-02
* **Description:** The backend shall enforce role-based permissions for protected operations. Authentication alone shall not grant permission to perform every action.
* **Verification:** Automated authorization tests, including direct API requests.

### FR-03: Honeypot Management
* **Priority:** Must | **Related user story:** US-03
* **Description:** The system shall allow authorized administrators to register and manage supported honeypot sources. The system shall maintain the information required to identify registered sources and associate incoming events with them.
* **Verification:** Honeypot registration, update, validation, and access-control tests.

### FR-04: Event Ingestion
* **Priority:** Must | **Related user story:** US-04
* **Description:** The backend shall accept security events from registered and supported sources through the documented ingestion interface. It shall reject invalid requests and requests that fail applicable source validation.
* **Verification:** Event-ingestion tests for valid input, malformed input, missing fields, and invalid source information.

### FR-05: Event Normalization and Storage
* **Priority:** Must | **Related user story:** US-05
* **Description:** The system shall convert supported incoming event formats into a documented common schema and persist valid normalized events.
* **Verification:** Schema-validation, normalization, persistence, and retrieval tests.

### FR-06: Detection Rules and Alerts
* **Priority:** Must | **Related user story:** US-06
* **Description:** The system shall evaluate configured basic detection rules against supported events and create alerts when the defined matching conditions are satisfied. Each implemented rule shall have documented matching conditions and an associated verification test.
* **Verification:** Positive matching tests, non-matching tests, and alert-persistence tests.

### FR-07: Dashboard and Event Search
* **Priority:** Must | **Related user story:** US-07
* **Description:** The system shall provide an interface through which authorized users can view and search stored events and alerts according to their permissions. The interface shall communicate loading, empty-result, and error states clearly.
* **Verification:** Frontend behavior tests and API integration tests.

### FR-08: Audit Logging
* **Priority:** Must | **Related user story:** US-08
* **Description:** The system shall record defined security-relevant administrative and access-related actions. Audit records shall contain, where applicable, the actor, action, timestamp, target resource, and outcome. Passwords, authentication secrets, and other explicitly prohibited sensitive values shall not be written to application audit logs.
* **Verification:** Audit completeness, outcome recording, and sensitive-data exclusion tests.

## 6. Non-Functional Requirements
Non-functional requirements define measurable quality, security, reliability, and operational expectations. Targets apply to the initial academic implementation.

### NFR-01: Authentication and Authorization Responses
* **Priority:** Must
* Protected API endpoints shall return:
  * `HTTP 401 Unauthorized` for requests without valid authentication, where authentication is required.
  * `HTTP 403 Forbidden` for authenticated requests that lack the required permission, where the endpoint uses this distinction.
* **Measurement procedure:** Send unauthenticated, invalid credential, and insufficient permission requests; record response statuses.
* **Pass criterion:** Observed responses conform to documented authentication/authorization behavior.

### NFR-02: Input Validation and Error Handling
* **Priority:** Must
* The backend shall reject malformed JSON, missing required fields, and invalid field values with an appropriate `HTTP 4xx` response when the request cannot be processed. Invalid input shall not terminate the backend process.
* **Measurement procedure:** Submit malformed JSON, missing required fields, and invalid types. Submit a valid event afterwards.
* **Pass criterion:** Invalid requests receive client-error responses; backend remains operational for subsequent valid requests.

### NFR-03: Event-Ingestion Response Time
* **Priority:** Must
* Under the documented local test environment, at least 95% of 100 valid event-ingestion requests shall receive a response in less than 500 milliseconds (excluding external network latency).
* **Measurement procedure:** Prepare 100 valid test events, record elapsed time, calculate the 95th percentile.
* **Pass criterion:** At least 95 of 100 measured requests complete in under 500 ms under stated conditions.

### NFR-04: Recovery After Invalid Requests
* **Priority:** Must
* After processing 100 malformed or otherwise invalid requests, the backend shall successfully process a subsequent valid event without requiring a restart.
* **Measurement procedure:** Submit 100 invalid requests, then submit a valid event and verify response behavior.
* **Pass criterion:** Valid event processes successfully; no restart required.

### NFR-05: Audit Completeness and Sensitive-Data Exclusion
* **Priority:** Must
* All successful administrative actions in the approved audit scope shall produce an audit record containing required actor, action, timestamp, and outcome fields. Passwords and secrets shall not be recorded.
* **Measurement procedure:** Execute administrative actions, compare with audit logs, inspect for sensitive values.
* **Pass criterion:** All tested actions have required audit records, and prohibited sensitive values are absent.

### NFR-06: Backend Access-Control Enforcement
* **Priority:** Must
* Protected administrative operations shall enforce permissions on the backend, including when requests are sent directly to the API without using the frontend.
* **Measurement procedure:** Authenticate as a non-admin, send direct requests to administrative endpoints, attempt modifications.
* **Pass criterion:** All unauthorized operations are denied by the backend.

### NFR-07: Dashboard Usability and State Handling
* **Priority:** Must
* The dashboard shall display a distinguishable state for: (1) Data loading, (2) Successful results, (3) No matching results, (4) API or server errors.
* **Measurement procedure:** Exercise each condition on the interface and observe the rendered states.
* **Pass criterion:** Each condition has a clear and distinguishable interface state.

### NFR-08: Common Event Schema
* **Priority:** Must
* Every supported integration shall map its supported input events to the documented common event schema defining required fields, data types, and timestamps.
* **Measurement procedure:** Submit representative events from each integration, validate normalized records against schema.
* **Pass criterion:** All tested supported integrations produce schema-conforming normalized events.

### NFR-09: Automated Test Coverage of Must Requirements
* **Priority:** Must
* Every implemented Must functional requirement shall have automated tests covering primary successful behavior and relevant failure or authorization cases.
* **Measurement procedure:** Review requirements, identify linked tests, run test suite, and verify outcomes.
* **Pass criterion:** Every implemented Must requirement has documented automated success/failure tests.

### NFR-10: Reproducible Development Setup
* **Priority:** Must
* A developer shall be able to set up the development environment using repository instructions without undocumented steps.
* **Measurement procedure:** Follow repository setup instructions in a clean environment from scratch, install dependencies, and run tests.
* **Pass criterion:** Application components and tests start successfully using committed instructions.

## 7. User Stories and BDD Acceptance Criteria
Acceptance criteria use the **Given / When / Then** format.

### US-01: User Authentication
* **File:** `docs/requirements/user-stories/US-01-authentication.md`
* **Related requirement:** FR-01 | **Priority:** Must
* **As a** registered user, **I want to** sign in securely **so that** I can access the HIVE functions permitted to me.
* **Scenarios:**
  * *Scenario 1 (Successful authentication):* Given a registered/enabled user with valid credentials, When correct credentials are submitted, Then the system authenticates the user and grants access.
  * *Scenario 2 (Invalid credentials):* Given a registered user account, When an incorrect password is submitted, Then access is rejected.
  * *Scenario 3 (Unknown account):* Given a non-existent account, When someone attempts to authenticate, Then the attempt is rejected.
  * *Scenario 4 (Disabled account):* Given a disabled user account, When authentication is attempted, Then access is denied.

### US-02: Role-Based Authorization
* **File:** `docs/requirements/user-stories/US-02-authorization.md`
* **Related requirement:** FR-02 | **Priority:** Must
* **As a** system administrator, **I want to** ensure permissions are enforced by the backend **so that** users cannot perform actions outside their assigned roles.
* **Scenarios:**
  * *Scenario 1 (Authorized operation):* Given an authenticated user with required permissions, When requesting an operation, Then the backend allows it.
  * *Scenario 2 (Unauthorized operation):* Given an authenticated user *without* required permissions, When directly requesting an administrative operation, Then the backend rejects the request.
  * *Scenario 3 (Unauthenticated operation):* Given a request without valid authentication targeting a protected endpoint, Then the backend rejects it.

### US-03: Honeypot Management
* **File:** `docs/requirements/user-stories/US-03-honeypot-management.md`
* **Related requirement:** FR-03 | **Priority:** Must
* **As a** system administrator, **I want to** register and manage honeypot sources **so that** HIVE can identify supported event sources.
* **Scenarios:**
  * *Scenario 1 (Register valid source):* Given an authorized administrator submitting valid registration, Then the system stores source information.
  * *Scenario 2 (Reject invalid registration):* Given missing or invalid required fields, Then the system rejects the registration and explains the validation failure.
  * *Scenario 3 (Deny unauthorized management):* Given a user without management permission attempting modifications, Then the backend denies the operation.

### US-04: Security Event Ingestion
* **File:** `docs/requirements/user-stories/US-04-event-ingestion.md`
* **Related requirement:** FR-04 | **Priority:** Must
* **As a** supported honeypot source, **I want to** submit security events to HIVE **so that** observed activity can be centrally processed.
* **Scenarios:**
  * *Scenario 1 (Accept valid event):* Given a registered source and valid payload submitted via ingestion interface, Then the backend accepts it.
  * *Scenario 2 (Reject malformed JSON):* Given malformed JSON, Then the backend returns a client-error response without terminating.
  * *Scenario 3 (Reject missing fields):* Given an omitted required field, Then the backend rejects the payload.
  * *Scenario 4 (Recovery after invalid input):* Given prior invalid requests, When a subsequent valid event is submitted, Then the backend remains operational.

### US-05: Event Normalization and Storage
* **File:** `docs/requirements/user-stories/US-05-event-normalization-storage.md`
* **Related requirement:** FR-05 | **Priority:** Must
* **As a** security analyst, **I want to** have events from supported sources normalized and stored in a common format **so that** I can review and compare them consistently.
* **Scenarios:**
  * *Scenario 1 (Normalize supported event):* Given a valid event in source format, When normalized, Then it maps to the common schema.
  * *Scenario 2 (Persist normalized event):* Given an event passing validation/normalization, When stored, Then it is persisted and retrievable.
  * *Scenario 3 (Reject invalid normalized record):* Given input violating the common schema, Then the system rejects/safely handles it.
  * *Scenario 4 (Preserve event meaning):* Given mapped field values, When normalized, Then they retain documented meaning and types.

### US-06: Detection Rules and Alerts
* **File:** `docs/requirements/user-stories/US-06-detection-alerts.md`
* **Related requirement:** FR-06 | **Priority:** Must
* **As a** security analyst, **I want to** have HIVE identify events matching configured detection rules **so that** I can review potentially suspicious activity.
* **Scenarios:**
  * *Scenario 1 (Generate alert):* Given an enabled rule and matching event, When evaluated, Then an alert with rule reference and event info is created.
  * *Scenario 2 (No alert for non-matching):* Given a non-matching event, Then no alert is generated.
  * *Scenario 3 (Persist alert):* Given an alert is successfully created, Then it is stored and retrievable by authorized users.
  * *Scenario 4 (Handle invalid rule configuration):* Given invalid rule config, Then the system rejects it and reports validation failure.

### US-07: Dashboard and Event Search
* **File:** `docs/requirements/user-stories/US-07-dashboard-search.md`
* **Related requirement:** FR-07 | **Priority:** Must
* **As a** security analyst, **I want to** view and search events and alerts through a dashboard **so that** I can investigate activity without querying the database manually.
* **Scenarios:**
  * *Scenario 1 (View events):* Given an authorized analyst, When opening the dashboard, Then authorized events are displayed.
  * *Scenario 2 (Search events):* When submitting a search query, Then matching events or a clear no-results state is displayed.
  * *Scenario 3 (View alerts):* When opening the alerts view, Then authorized alerts are displayed.
  * *Scenario 4 (Handle API error):* Given an API error, When loading dashboard, Then an error state is displayed (not a false empty result).
  * *Scenario 5 (Handle loading state):* While waiting for a response, Then the interface communicates loading.

### US-08: Audit Logging
* **File:** `docs/requirements/user-stories/US-08-audit-logging.md`
* **Related requirement:** FR-08 | **Priority:** Must
* **As a** system administrator or authorized reviewer, **I want to** have security-relevant administrative actions recorded **so that** important changes can be investigated.
* **Scenarios:**
  * *Scenario 1 (Record successful administrative action):* Given an authorized admin action completes, Then an audit record contains actor, action, timestamp, and outcome.
  * *Scenario 2 (Record failed action):* Given a failed audited operation, Then the failure outcome is safely recorded.
  * *Scenario 3 (Exclude sensitive values):* Given an audited operation, Then passwords and authentication secrets are excluded from logs.
  * *Scenario 4 (Restrict audit access):* Given an unauthorized user, When attempting to access audit logs, Then access is denied.

## 10. Security and Data-Handling Requirements

### 10.1 Authentication and Secrets
* Passwords must not be stored in plaintext.
* Authentication secrets must not be committed to the repository.
* Use environment variables or approved configuration mechanisms.
* Error messages must not disclose tokens or sensitive data.

### 10.2 Authorization
* Backend operations must enforce required permissions. Frontend restrictions do not replace backend authorization.
* Access to audit records must follow the permission model.

### 10.3 Input Validation
* Backend must validate request structure and required fields. Invalid input must not terminate service.
* Test data must be synthetic or approved for academic use.

### 10.4 Audit Logs
* Audit records should contain only necessary investigation info. Passwords and secrets must never be logged.

### 10.5 Safe Testing
* Testing must be restricted to authorized systems, honeypots, and test data.
