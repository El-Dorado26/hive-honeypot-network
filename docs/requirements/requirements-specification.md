## 1. Introduction

### 1.1 Purpose

HIVE is a modular honeypot network platform designed to collect, validate, normalize, store, and visualize security events generated by honeypots. The platform aims to help users observe suspicious activity, review security events, identify basic attack patterns, and investigate potentially malicious behavior through a centralized interface.

This document defines the functional requirements, non-functional requirements, user stories, acceptance criteria, verification procedures, and traceability relationships for HIVE.

It serves as the primary requirements reference for implementation, testing, project planning, and evaluation.

### 1.2 Problem Statement

Honeypots can generate useful information about scanning, attempted exploitation, suspicious connections, and other potentially malicious activities. However, collecting and analyzing data from multiple honeypots can be difficult when each source produces different event formats or requires a separate monitoring interface.

HIVE aims to address this problem by providing a centralized platform that accepts events from supported honeypots, converts them into a common format, stores them, and presents relevant information through a dashboard.

The project will also explore basic detection rules, alert generation, access control, and security auditing. Its effectiveness will be evaluated through documented requirements and repeatable tests rather than unsupported claims about production readiness.

### 1.3 Objectives

The primary objectives are to:

1. Provide authentication for registered platform users.
2. Enforce role-based authorization on protected backend operations.
3. Register and manage supported honeypot sources.
4. Receive and validate security events from registered sources.
5. Normalize and store supported events in a common schema.
6. Evaluate configurable detection rules and generate alerts.
7. Provide authorized users with an interface for searching and reviewing events and alerts.
8. Record relevant administrative and security-related actions in audit logs.
9. Verify functional and non-functional requirements through automated and documented tests.
10. Provide reproducible setup and usage documentation.

### 1.4 Intended Audience

This document is intended for:

- Project team members responsible for implementation and testing.
- The project supervisor and course instructors.
- Reviewers evaluating the requirements, design, and verification process.
- Future developers extending the HIVE platform.

## 2. Project Scope

### 2.1 In Scope

The initial version of HIVE will include the following capabilities:

- A backend service implemented in Go.
- A REST API for supported platform operations.
- PostgreSQL for persistent storage.
- A React-based web interface.
- Authentication for registered users.
- Backend role-based authorization.
- Honeypot registration and management.
- Event ingestion and input validation.
- A common event schema for supported integrations.
- Persistent storage and retrieval of security events.
- Basic configurable detection rules and alert generation.
- Dashboard functionality for viewing and searching events and alerts.
- Audit logging for relevant security and administrative operations.
- Automated tests and a continuous integration workflow.
- Documentation covering setup, configuration, testing, and limitations.

SSH and HTTP/web honeypot integrations are intended initial integrations. Additional integrations will depend on implementation progress and feasibility.

The use of Elasticsearch, a simulated API honeypot, and other supporting components remains subject to the team's final architecture decisions. These components must not be described as implemented until verified in the repository.

### 2.2 Out of Scope

The following are excluded from the initial required scope:

- Replacing a production Security Information and Event Management (SIEM) or Security Operations Center (SOC) platform.
- Processing sensitive production data from hospitals, schools, or other organizations.
- Deploying unauthorized offensive infrastructure or conducting unauthorized attacks.
- Guaranteeing the detection of every attack or malicious activity.
- Supporting every possible honeypot protocol or event format.
- Claiming production-grade availability, scalability, or security without appropriate testing.
- Implementing complex machine-learning-based threat detection as a mandatory feature.
- Integrations that significantly delay completion of the core requirements.

### 2.3 Stretch Goals

The following features may be considered after the core requirements are satisfied:

- Additional honeypot integrations.
- Attacker fingerprinting and behavioral analysis.
- MITRE ATT&CK technique mapping.
- IOC extraction and threat intelligence export.
- Session replay or richer interaction analysis.
- Advanced detection rules.
- Additional visualization and reporting capabilities.

Stretch goals will not be considered mandatory acceptance criteria unless formally added to the approved requirements.

### 2.4 Assumptions and Constraints

The project assumes that:

1. Event sources can communicate with the HIVE backend through a supported interface.
2. The development environment can run the required software and database services.
3. The team can use synthetic or non-sensitive test data.
4. The initial deployment will be intended for academic demonstration and evaluation.
5. The system's security claims will be limited to properties demonstrated by its implementation and tests.

Constraints include the project deadline, team capacity, available computing resources, and the need to prioritize working core features over optional integrations.

## 4. System Overview and Architecture

### 4.1 Proposed Architecture

HIVE is designed around the following logical components:

1. **Honeypot and Event Sources:** Generate security-related events.
2. **Backend REST API:** Receives requests, validates input, and enforces applicable access controls.
3. **Event Processing Component:** Normalizes supported event formats and passes valid events for storage and analysis.
4. **Detection Component:** Evaluates configured rules and creates alerts when matching conditions are satisfied.
5. **PostgreSQL Database:** Stores users, roles or permissions, honeypot registrations, events, alerts, and audit records as required by the final schema.
6. **React Dashboard:** Allows authorized users to view and search available information.
7. **Testing and CI:** Runs automated checks against implemented requirements and relevant security controls.

Elasticsearch may be introduced if the team confirms that it is necessary for the selected event-search or analysis functionality. PostgreSQL remains the required persistent database for the initial architecture.

### 4.2 High-Level Data Flow

The intended event-processing flow is:

1. A supported honeypot generates an event.
2. The source submits the event through the supported API or integration.
3. The backend validates the request and required fields.
4. Valid events are converted into the common event schema.
5. The normalized event is stored.
6. The detection component evaluates applicable rules.
7. Matching rules create alerts.
8. Authorized users retrieve and review events and alerts through the dashboard.

The final implementation may use synchronous or asynchronous processing. The team must document the actual processing model and ensure that the acceptance criteria remain consistent with it.

### 4.3 Actors

| Actor | Description |
|---|---|
| System Administrator | Manages platform configuration, users, roles, and honeypot registrations, subject to the implemented permissions. |
| Security Analyst | Reviews events and alerts and searches security information permitted by their role. |
| Honeypot / Event Source | Submits security events through a supported integration. |
| Automated Test Runner | Executes verification tests in the development or CI environment. |

The Automated Test Runner is a verification participant rather than a human application user.

## 5. Functional Requirements

Functional requirements describe what the system must do.

Priority definitions:

- **Must:** Required for the initial deliverable.
- **Should:** Important but may be deferred if justified and approved.
- **Could:** Optional enhancement.

### FR-01: User Authentication

**Priority:** Must

The system shall authenticate registered users before granting access to protected application functionality.

**Related user story:** US-01

**Verification:** Automated authentication tests.

### FR-02: Role-Based Authorization

**Priority:** Must

The backend shall enforce role-based permissions for protected operations. Authentication alone shall not grant permission to perform every action.

**Related user story:** US-02

**Verification:** Automated authorization tests, including direct API requests.

### FR-03: Honeypot Management

**Priority:** Must

The system shall allow authorized administrators to register and manage supported honeypot sources. The system shall maintain the information required to identify registered sources and associate incoming events with them.

**Related user story:** US-03

**Verification:** Honeypot registration, update, validation, and access-control tests.

### FR-04: Event Ingestion

**Priority:** Must

The backend shall accept security events from registered and supported sources through the documented ingestion interface. It shall reject invalid requests and requests that fail applicable source validation.

**Related user story:** US-04

**Verification:** Event-ingestion tests for valid input, malformed input, missing fields, and invalid source information.

### FR-05: Event Normalization and Storage

**Priority:** Must

The system shall convert supported incoming event formats into a documented common schema and persist valid normalized events.

**Related user story:** US-05

**Verification:** Schema-validation, normalization, persistence, and retrieval tests.

### FR-06: Detection Rules and Alerts

**Priority:** Must

The system shall evaluate configured basic detection rules against supported events and create alerts when the defined matching conditions are satisfied.

Each implemented rule shall have documented matching conditions and an associated verification test.

**Related user story:** US-06

**Verification:** Positive matching tests, non-matching tests, and alert-persistence tests.

### FR-07: Dashboard and Event Search

**Priority:** Must

The system shall provide an interface through which authorized users can view and search stored events and alerts according to their permissions.

The interface shall communicate loading, empty-result, and error states clearly.

**Related user story:** US-07

**Verification:** Frontend behavior tests and API integration tests.

### FR-08: Audit Logging

**Priority:** Must

The system shall record defined security-relevant administrative and access-related actions. Audit records shall contain, where applicable, the actor, action, timestamp, target resource, and outcome.

Passwords, authentication secrets, and other explicitly prohibited sensitive values shall not be written to application audit logs.

**Related user story:** US-08

**Verification:** Audit completeness, outcome recording, and sensitive-data exclusion tests.

## 6. Non-Functional Requirements

Non-functional requirements define measurable quality, security, reliability, and operational expectations.

The targets below apply to the initial academic implementation. Any change to a target must be documented and justified rather than silently weakening the requirement.

### NFR-01: Authentication and Authorization Responses

**Priority:** Must

Protected API endpoints shall return:

- HTTP `401 Unauthorized` for requests without valid authentication, where authentication is required.
- HTTP `403 Forbidden` for authenticated requests that lack the required permission, where the endpoint uses this distinction.

**Measurement procedure:**

1. Send a request to a protected endpoint without credentials.
2. Send a request with invalid credentials.
3. Send a request with valid credentials but insufficient permissions.
4. Record the response status for each case.

**Pass criterion:** The observed responses conform to the documented authentication and authorization behavior.

### NFR-02: Input Validation and Error Handling

**Priority:** Must

The backend shall reject malformed JSON, missing required fields, and invalid field values with an appropriate HTTP `4xx` response when the request cannot be processed.

Invalid input shall not terminate the backend process.

**Measurement procedure:**

1. Submit malformed JSON.
2. Submit valid JSON with required fields omitted.
3. Submit values with invalid formats or types.
4. Verify that each invalid request is rejected.
5. Submit a valid event after the invalid requests.

**Pass criterion:** Invalid requests receive suitable client-error responses, and the backend remains able to process subsequent valid requests.

### NFR-03: Event-Ingestion Response Time

**Priority:** Must

Under the documented local test environment, at least 95% of 100 valid event-ingestion requests shall receive a response in less than 500 milliseconds.

The measurement shall exclude external network latency and shall document whether database writes, normalization, and other processing are included in the measured interval.

**Measurement procedure:**

1. Record the hardware, operating system, backend configuration, and database configuration.
2. Prepare 100 valid test events.
3. Record the elapsed time for each request.
4. Calculate the 95th percentile response time.
5. Preserve the test output as verification evidence.

**Pass criterion:** At least 95 of the 100 measured requests complete in less than 500 milliseconds under the stated conditions.

This is a local academic benchmark, not a production scalability guarantee.

### NFR-04: Recovery After Invalid Requests

**Priority:** Must

After processing 100 malformed or otherwise invalid requests, the backend shall successfully process a subsequent valid event without requiring a restart.

**Measurement procedure:**

1. Start the backend in the documented test environment.
2. Submit 100 invalid requests.
3. Submit a valid event.
4. Verify the valid event's response and expected processing behavior.
5. Confirm that the process remained operational.

**Pass criterion:** The valid event is processed successfully and the backend does not require a restart.

### NFR-05: Audit Completeness and Sensitive-Data Exclusion

**Priority:** Must

All successful administrative actions included in the approved audit scope shall produce an audit record containing the required actor, action, timestamp, and outcome fields.

Where an operation fails, its outcome shall be recorded when that operation is within the defined audit scope and the failure can be safely logged.

Passwords, authentication secrets, and prohibited sensitive values shall not be recorded in audit logs.

**Measurement procedure:**

1. Execute every administrative action in the approved audit scope.
2. Compare the executed actions with the resulting audit records.
3. Verify that required fields are populated.
4. Inspect records and application logs for prohibited values.

**Pass criterion:** All tested successful administrative actions have the required audit records, and prohibited sensitive values are absent.

### NFR-06: Backend Access-Control Enforcement

**Priority:** Must

Protected administrative operations shall enforce permissions on the backend, including when requests are sent directly to the API without using the frontend.

**Measurement procedure:**

1. Authenticate as a user without administrative privileges.
2. Send direct requests to administrative endpoints.
3. Attempt to modify users, roles, or honeypot registrations where applicable.
4. Verify that unauthorized operations are rejected and that protected data is not modified.

**Pass criterion:** All tested unauthorized operations are denied by the backend.

Hiding a frontend button is not sufficient to satisfy this requirement.

### NFR-07: Dashboard Usability and State Handling

**Priority:** Must

The dashboard shall display a distinguishable state for:

1. Data loading.
2. Successful results.
3. No matching results.
4. API or server errors.

The interface shall not present a failed request as a successful empty result.

**Measurement procedure:**

1. Load a dashboard view while data is being retrieved.
2. Load the view with available records.
3. search for a value with no matching records.
4. Simulate an API error.
5. Observe the interface in each condition.

**Pass criterion:** Each condition has a clear and distinguishable interface state.

### NFR-08: Common Event Schema

**Priority:** Must

Every supported integration shall map its supported input events to the documented common event schema.

The schema shall define the required fields, data types, optional fields, timestamp representation, and validation rules.

**Measurement procedure:**

1. Submit representative events from each supported integration.
2. Validate the normalized records against the documented schema.
3. Check that required fields have consistent meanings and types.
4. Confirm that invalid or unmappable required data is handled according to documented rules.

**Pass criterion:** All tested supported integrations produce schema-conforming normalized events.

### NFR-09: Automated Test Coverage of Must Requirements

**Priority:** Must

Every implemented Must functional requirement shall have automated tests covering its primary successful behavior and relevant failure or authorization cases.

Where a requirement cannot yet be implemented, its test shall be documented as pending or expected to fail until implementation is complete.

**Measurement procedure:**

1. Review the functional requirements and their linked user stories.
2. Identify the automated tests associated with each requirement.
3. Run the relevant test suite.
4. Record test outcomes and unresolved failures.
5. Verify that unimplemented requirements are not incorrectly reported as passing.

**Pass criterion:** Every implemented Must requirement has documented automated success and relevant failure tests, and outstanding tests are clearly identified.

### NFR-10: Reproducible Development Setup

**Priority:** Must

A developer shall be able to set up the documented development environment using the repository instructions and declared prerequisites without relying on undocumented configuration steps.

**Measurement procedure:**

1. Use a clean development environment or clean test setup.
2. Follow the repository's setup instructions from the beginning.
3. Install the declared dependencies.
4. Configure the required environment variables and database.
5. Start the documented services.
6. Run the available automated tests.

**Pass criterion:** The application components and documented tests can be started using the committed instructions and declared prerequisites. Any known limitation must be documented.

## 7. User Stories and BDD Acceptance Criteria

Each user story shall be maintained as an individual Markdown file in:

Acceptance criteria use the Given/When/Then format:

- **Given:** The initial context or condition.
- **When:** The action or event being tested.
- **Then:** The expected result.

The scenarios below define the required behavior. They are not evidence that the behavior has already been implemented.

### US-01: User Authentication

**File:** `docs/requirements/user-stories/US-01-authentication.md`  
**Related requirement:** FR-01  
**Priority:** Must

**User story**

As a registered user, I want to sign in securely so that I can access the HIVE functions permitted to me.

**Acceptance criteria**

**Scenario 1: Successful authentication**

- Given a registered and enabled user with valid credentials,
- When the user submits the correct credentials,
- Then the system authenticates the user and grants access according to the user's permissions.

**Scenario 2: Invalid credentials**

- Given a registered user account,
- When the user submits an incorrect password,
- Then the system rejects the authentication attempt and does not grant protected access.

**Scenario 3: Unknown account**

- Given an account that does not exist,
- When someone attempts to authenticate using that account,
- Then the system rejects the attempt without granting protected access.

**Scenario 4: Disabled account**

- Given a disabled user account,
- When the user attempts to authenticate,
- Then the system denies access.

**Verification:** Test valid credentials, invalid credentials, unknown accounts, and disabled accounts.

## 8. Verification and Testing Strategy

### 8.1 Testing Approach

HIVE shall use a combination of:

- Unit tests for validation, normalization, detection rules, and other isolated behavior.
- API tests for request handling, authentication, authorization, and error responses.
- Integration tests for database persistence and interactions between components.
- Frontend tests for dashboard states and user interactions.
- Non-functional tests for response time, recovery, and other measurable quality targets.
- Manual verification where automation is not practical, with recorded steps and evidence.

Automated tests should be repeatable and use controlled test data. Tests must not depend on unauthorized external systems or real sensitive production data.

### 8.2 Acceptance-Test Status

The project must distinguish between:

1. **Prototype tests:** Tests for a limited component or preliminary implementation.
2. **Requirement acceptance tests:** Tests linked to the behavior defined in a specific user story.
3. **Non-functional tests:** Tests that measure quality attributes such as response time or recovery.
4. **Manual verification:** Documented checks that cannot yet be fully automated.

Passing prototype tests do not establish that the complete system satisfies all functional requirements.

For example, passing tests for JSON validation or handler recovery do not demonstrate that authentication, role-based authorization, database persistence, alert generation, or dashboard behavior is complete.

### 8.3 Test Development Status

The project team has previously reported six passing Go prototype tests covering:

- Malformed JSON rejection.
- Missing required fields.
- Valid event acceptance.
- Unsupported HTTP methods.
- Handler recovery after invalid requests.
- Preliminary handler response-time measurement.

These results must be confirmed against the current repository and test output before being treated as current verification evidence.

The tests should be identified as prototype or handler-level tests where appropriate. They must not be represented as complete acceptance coverage for FR-01 through FR-08.

## 10. Security and Data-Handling Requirements

HIVE is a cybersecurity monitoring project and must follow safe development practices.

### 10.1 Authentication and Secrets

- Passwords must not be stored in plaintext.
- Authentication secrets must not be committed to the repository.
- Configuration requiring secrets should use documented environment variables or another approved configuration mechanism.
- Error messages must not disclose passwords, tokens, or other sensitive authentication data.

The exact authentication and password-storage implementation must be documented and verified against the code.

### 10.2 Authorization

- Backend operations must enforce their required permissions.
- Frontend restrictions must not be treated as a replacement for backend authorization.
- Access to audit records and administrative functionality must follow the documented permission model.

### 10.3 Input Validation

- The backend must validate request structure and required fields.
- Invalid input must not cause the service to terminate.
- Event processing must handle unsupported or malformed data according to a documented policy.
- Test data should be synthetic or otherwise approved for academic use.

### 10.4 Audit Logs

- Audit records should contain only the information needed for accountability and investigation.
- Passwords and prohibited authentication secrets must not be logged.
- Audit-log access must be controlled.
- The project must document any limitations in audit completeness or tamper resistance.

### 10.5 Safe Testing

Testing must be limited to systems, honeypots, environments, and data that the team is authorized to use.

The project does not claim to provide a complete production security certification. Its security properties must be evaluated against the implemented controls and the evidence collected.
