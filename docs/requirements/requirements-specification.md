## 1. Introduction

### 1.1 Purpose

HIVE is a modular honeypot network platform that collects, validates, normalizes, stores and visualizes security events generated by honeypots. It lets users observe suspicious activity, review events, identify basic attack patterns and investigate potentially malicious behavior through one centralized interface.

This document is the primary requirements reference for HIVE. It defines the functional and non-functional requirements, user stories with acceptance criteria, the verification approach, and the current verification status of each requirement.

### 1.2 Problem Statement

Honeypots produce useful information about scanning, attempted exploitation and suspicious connections. Analyzing data from several honeypots is difficult when each source uses a different event format or needs its own monitoring interface.

HIVE addresses this by accepting events from supported honeypots, converting them to a common format, storing them and presenting them on a dashboard. It also provides basic detection rules, alert generation, access control and security auditing. Its effectiveness is assessed through documented requirements and repeatable tests, not through claims of production readiness.

### 1.3 Objectives

- Authenticate registered platform users.
- Enforce role-based authorization on protected backend operations.
- Register and manage supported honeypot sources.
- Receive and validate security events from registered sources.
- Normalize and store supported events in a common schema.
- Evaluate configurable detection rules and generate alerts.
- Let authorized users search and review events and alerts.
- Record relevant administrative and security-related actions in audit logs.
- Verify functional and non-functional requirements through automated and documented tests.
- Provide reproducible setup and usage documentation.

### 1.4 Intended Audience

Project team members, the project supervisor and course instructors, reviewers of the requirements and verification process, and future developers extending HIVE.

### 1.5 Current Status

This version of the specification is a draft. All requirements in Sections 5 and 6 are defined. The only recorded test evidence is a set of six Go prototype tests covering event-handler behavior (Section 8.3). Requirement-level verification status is given in Sections 8.4 and 8.5, and the status of each design decision in Section 10.

## 2. Project Scope

### 2.1 In Scope

- Backend service implemented in Go, exposing a REST API for platform operations.
- PostgreSQL for persistent storage; React-based web interface.
- User authentication and backend role-based authorization.
- Honeypot registration and management.
- Event ingestion with input validation, and a common event schema for supported integrations.
- Persistent storage and retrieval of security events.
- Basic configurable detection rules and alert generation.
- Dashboard for viewing and searching events and alerts.
- Audit logging for relevant security and administrative operations.
- Automated tests, a continuous integration workflow, and documentation of setup, configuration, testing and limitations.

SSH and HTTP/web honeypots are the intended initial integrations. Further integrations depend on implementation progress and feasibility. Elasticsearch and a simulated API honeypot are optional components and are not required by this specification.

### 2.2 Out of Scope

- Replacing a production SIEM or SOC platform.
- Processing sensitive production data from hospitals, schools or other organizations.
- Deploying unauthorized offensive infrastructure or conducting unauthorized attacks.
- Guaranteeing detection of every attack or malicious activity.
- Supporting every possible honeypot protocol or event format.
- Claiming production-grade availability, scalability or security.
- Machine-learning-based threat detection as a mandatory feature.
- Integrations that would significantly delay the core requirements.

### 2.3 Stretch Goals

The following are possible extensions beyond the core requirements and are not mandatory acceptance criteria unless formally added: additional honeypot integrations; attacker fingerprinting and behavioral analysis; MITRE ATT&CK technique mapping; IOC extraction and threat-intelligence export; session replay; advanced detection rules; additional visualization and reporting.

### 2.4 Assumptions and Constraints

The project assumes that event sources can reach the HIVE backend through a supported interface; that the development environment can run the required software and database services; that synthetic or non-sensitive test data is used; that the initial deployment is for academic demonstration and evaluation; and that security claims are limited to properties demonstrated by the implementation and tests. Constraints are the project deadline, team capacity, available computing resources, and the priority of working core features over optional integrations.

## 4. System Overview and Architecture

### 4.1 Architecture

HIVE consists of the following logical components:

- **Honeypots and event sources** generate security-related events.
- **Backend REST API** receives requests, validates input and enforces access control.
- **Event processing component** normalizes supported event formats and passes valid events on for storage and analysis.
- **Detection component** evaluates configured rules and creates alerts when conditions match.
- **PostgreSQL database** stores users, roles and permissions, honeypot registrations, events, alerts and audit records.
- **React dashboard** lets authorized users view and search events and alerts.
- **Testing and CI** run automated checks against implemented requirements and security controls.

PostgreSQL is the required persistent database. Elasticsearch is optional and is included only if the selected search functionality needs it.

### 4.2 Event Data Flow

A supported honeypot generates an event and submits it through the supported API or integration. The backend validates the request and required fields, converts valid events to the common event schema and stores the normalized event. The detection component then evaluates applicable rules, and matching rules create alerts. Authorized users retrieve and review events and alerts through the dashboard. Processing may be synchronous or asynchronous.

### 4.3 Actors

| Actor | Description |
|---|---|
| System Administrator | Manages platform configuration, users, roles and honeypot registrations, subject to the implemented permissions. |
| Security Analyst | Reviews events and alerts and searches security information permitted by their role. |
| Honeypot / Event Source | Submits security events through a supported integration. |
| Automated Test Runner | Executes verification tests in the development or CI environment. It is a verification participant, not a human application user, and is therefore not shown in the use case diagram. |

## 5. Functional Requirements

Priorities: **Must** is required for the initial deliverable; **Should** is important but may be deferred if justified and approved; **Could** is an optional enhancement. All eight functional requirements below are Must.

### FR-01: User Authentication

*Priority: Must | User story: US-01*

The system shall authenticate registered users before granting access to protected application functionality.

**Verification:** Automated authentication tests.

### FR-02: Role-Based Authorization

*Priority: Must | User story: US-02*

The backend shall enforce role-based permissions for protected operations. Authentication alone shall not grant permission to perform every action.

**Verification:** Automated authorization tests, including direct API requests.

### FR-03: Honeypot Management

*Priority: Must | User story: US-03*

The system shall allow authorized administrators to register and manage supported honeypot sources, and shall maintain the information needed to identify registered sources and associate incoming events with them.

**Verification:** Registration, update, validation and access-control tests.

### FR-04: Event Ingestion

*Priority: Must | User story: US-04*

The backend shall accept security events from registered and supported sources through the documented ingestion interface, and shall reject invalid requests and requests that fail source validation.

**Verification:** Ingestion tests for valid input, malformed input, missing fields and invalid source information.

### FR-05: Event Normalization and Storage

*Priority: Must | User story: US-05*

The system shall convert supported incoming event formats into a documented common schema and persist valid normalized events.

**Verification:** Schema-validation, normalization, persistence and retrieval tests.

### FR-06: Detection Rules and Alerts

*Priority: Must | User story: US-06*

The system shall evaluate configured basic detection rules against supported events and create alerts when the defined conditions match. Each implemented rule shall have documented matching conditions and an associated verification test.

**Verification:** Positive-match, non-match and alert-persistence tests.

### FR-07: Dashboard and Event Search

*Priority: Must | User story: US-07*

The system shall provide an interface through which authorized users can view and search stored events and alerts according to their permissions, and shall communicate loading, empty-result and error states clearly.

**Verification:** Frontend behavior tests and API integration tests.

### FR-08: Audit Logging

*Priority: Must | User story: US-08*

The system shall record defined security-relevant administrative and access-related actions. Audit records shall contain, where applicable, the actor, action, timestamp, target resource and outcome. Passwords, authentication secrets and other prohibited sensitive values shall not be written to audit logs.

**Verification:** Audit completeness, outcome recording and sensitive-data exclusion tests.

## 6. Non-Functional Requirements

The targets below apply to the initial academic implementation. All are Must.

| ID | Requirement | Measurement | Pass criterion |
|---|---|---|---|
| **NFR-01** Authentication and authorization responses | Protected endpoints return HTTP 401 for requests without valid authentication and HTTP 403 for authenticated requests lacking the required permission. | Send requests with no credentials, invalid credentials, and valid credentials with insufficient permissions; record each status. | Observed responses match the documented behavior. |
| **NFR-02** Input validation and error handling | The backend rejects malformed JSON, missing required fields and invalid values with an appropriate 4xx response. Invalid input does not terminate the process. | Submit malformed JSON, JSON with omitted fields, and invalid formats or types; then submit a valid event. | Every invalid request is rejected with a client error and the subsequent valid event is processed. |
| **NFR-03** Event-ingestion response time | In the documented local test environment, at least 95% of 100 valid ingestion requests respond in under 500 ms. External network latency is excluded, and the report states whether database writes and normalization are inside the measured interval. | Record hardware, OS, and backend and database configuration; send 100 valid events; record per-request time; compute the 95th percentile; keep the output. | At least 95 of 100 requests complete in under 500 ms. This is a local academic benchmark, not a scalability guarantee. |
| **NFR-04** Recovery after invalid requests | After 100 malformed or invalid requests, the backend processes a valid event without a restart. | Start the backend, submit 100 invalid requests, submit a valid event, confirm the process stayed up. | The valid event is processed and no restart is needed. |

Failures within scope are recorded where they can be logged safely. Hiding a frontend button does not satisfy this requirement. |

| **NFR-08** Common event schema | Every supported integration maps its input events to the documented common schema, which defines required and optional fields, data types, timestamp representation and validation rules. | Submit representative events from each integration, validate normalized records against the schema, check field meaning and type consistency, and check handling of unmappable data. | All tested integrations produce schema-conforming events. |

Tests for unimplemented requirements are marked pending or expected-to-fail. | Map requirements and stories to tests, run the suite, record outcomes, and confirm unimplemented requirements are not reported as passing. | Each implemented Must requirement has documented success and failure tests; pending tests are identified. |

## 7. User Stories and Acceptance Criteria

Acceptance criteria use the Given/When/Then format. Each scenario defines required behavior; implementation status is reported in Section 8.4.

### US-01: User Authentication

*Related requirement: FR-01 | Priority: Must*

> As a registered user, I want to sign in securely so that I can access the HIVE functions permitted to me.

**Scenario 1: Successful authentication.** **Given** a registered and enabled user with valid credentials, **when** the user submits the correct credentials, **then** the system authenticates the user and grants access according to their permissions.

**Scenario 2: Invalid credentials.** **Given** a registered user account, **when** the user submits an incorrect password, **then** the system rejects the attempt and grants no protected access.

**Scenario 3: Unknown account.** **Given** an account that does not exist, **when** someone attempts to authenticate with it, **then** the system rejects the attempt without granting protected access.

**Scenario 4: Disabled account.** **Given** a disabled user account, **when** the user attempts to authenticate, **then** the system denies access.

**Verification:** Valid credentials, invalid credentials, unknown accounts and disabled accounts.

### US-02: Role-Based Authorization

*Related requirement: FR-02 | Priority: Must*

> As a system administrator, I want permissions to be enforced by the backend so that users cannot perform actions outside their assigned roles.

**Scenario 1: Authorized operation.** **Given** an authenticated user with the permission required for an operation, **when** the user requests it, **then** the backend allows it if all other validation conditions are satisfied.

**Scenario 2: Unauthorized operation.** **Given** an authenticated user without the required permission, **when** the user directly requests a protected administrative operation, **then** the backend rejects the request and does not perform the operation.

**Scenario 3: Unauthenticated operation.** **Given** a request without valid authentication, **when** it targets a protected endpoint, **then** the backend rejects it according to the documented authentication behavior.

**Verification:** Authorized, unauthorized and unauthenticated requests against protected endpoints.

### US-03: Honeypot Management

*Related requirement: FR-03 | Priority: Must*

> As a system administrator, I want to register and manage honeypot sources so that HIVE can identify supported event sources.

**Scenario 1: Register a valid source.** **Given** an authenticated administrator with the required permission, **when** they submit a valid honeypot registration, **then** the system validates it and stores the source information.

**Scenario 2: Reject invalid registration.** **Given** an authenticated administrator, **when** they submit a registration with missing or invalid required fields, **then** the system rejects it and explains the validation failure.

**Scenario 3: Deny unauthorized management.** **Given** an authenticated user without honeypot-management permission, **when** they attempt to create or modify a registration, **then** the backend denies the operation and applies no change.

**Verification:** Valid registration, invalid registration, updates and access-control enforcement.

### US-04: Security Event Ingestion

*Related requirement: FR-04 | Priority: Must*

> As a supported honeypot source, I want to submit security events to HIVE so that observed activity can be centrally processed.

**Scenario 1: Accept a valid event.** **Given** a registered and supported source and a valid payload, **when** the source submits the event through the documented interface, **then** the backend validates the request and accepts it for processing.

**Scenario 2: Reject malformed input.** **Given** a source submits malformed JSON, **when** the backend processes the request, **then** it returns a client-error response and does not terminate.

**Scenario 3: Reject missing required fields.** **Given** a payload that omits a required field, **when** the backend validates it, **then** it rejects the payload, identifies the failure and does not store it as a valid event.

**Scenario 4: Recover after invalid input.** **Given** the backend has processed invalid requests, **when** a valid event is submitted, **then** the backend remains operational and processes it normally.

**Verification:** Valid events, malformed JSON, missing fields, invalid source information and recovery.

### US-05: Event Normalization and Storage

*Related requirement: FR-05 | Priority: Must*

> As a security analyst, I want events from supported sources to be normalized and stored in a common format so that I can review and compare them consistently.

**Scenario 1: Normalize a supported event.** **Given** a valid event in a supported source format, **when** it enters normalization, **then** the system maps it to the documented common schema.

**Scenario 2: Persist a normalized event.** **Given** an event that passes validation and normalization, **when** storage completes successfully, **then** it is persisted and retrievable through an authorized operation.

**Scenario 3: Reject an invalid normalized record.** **Given** an input that cannot satisfy the common schema, **when** the system attempts to normalize it, **then** the system rejects or safely handles it according to the documented error policy.

**Scenario 4: Preserve event meaning.** **Given** a supported input event with defined field mappings, **when** the system normalizes it, **then** mapped values retain their documented meaning and types.

**Verification:** Field mapping, schema validation, persistence and retrieval.

### US-06: Detection Rules and Alerts

*Related requirement: FR-06 | Priority: Must*

> As a security analyst, I want HIVE to identify events matching configured detection rules so that I can review potentially suspicious activity.

**Scenario 1: Alert for a matching event.** **Given** an enabled rule and an event satisfying its conditions, **when** the system evaluates the event, **then** it creates an alert with the documented rule reference and relevant event information.

**Scenario 2: No alert for a non-matching event.** **Given** an enabled rule and an event that does not satisfy it, **when** the system evaluates the event, **then** it generates no alert for that rule.

**Scenario 3: Persist a generated alert.** **Given** an event that triggers an enabled rule, **when** alert creation succeeds, **then** the alert is stored and retrievable by an authorized user.

**Scenario 4: Invalid rule configuration.** **Given** a rule configuration that fails validation, **when** an authorized user tries to save or enable it, **then** the system rejects it and reports the validation failure.

**Verification:** Matching events, non-matching events, alert persistence and invalid rule configuration.

### US-07: Dashboard and Event Search

*Related requirement: FR-07 | Priority: Must*

> As a security analyst, I want to view and search events and alerts through a dashboard so that I can investigate activity without querying the database manually.

**Scenario 1: View available events.** **Given** an authenticated analyst with the required permissions and stored events, **when** they open the event dashboard, **then** it displays the events they are authorized to view.

**Scenario 2: Search for events.** **Given** stored events and an available search interface, **when** the analyst submits a supported query, **then** the interface shows matching events or a clear no-results state.

**Scenario 3: View alerts.** **Given** stored alerts and an authenticated analyst with the required permissions, **when** they open the alerts view, **then** it displays the alerts they are authorized to view.

**Scenario 4: Handle an API error.** **Given** the dashboard cannot retrieve data because the API returns an error, **when** the interface processes the failed request, **then** it shows an error state rather than a successful empty result.

**Scenario 5: Handle loading state.** **Given** a dashboard request is in progress, **when** the interface is waiting for the response, **then** it communicates that data is loading.

**Verification:** Populated results, search results, empty results, loading behavior, API errors and permissions.

### US-08: Audit Logging

*Related requirement: FR-08 | Priority: Must*

> As a system administrator or authorized reviewer, I want security-relevant administrative actions to be recorded so that important changes can be investigated.

**Scenario 1: Record a successful administrative action.** **Given** an authenticated administrator performs an in-scope action, **when** it completes successfully, **then** the system creates an audit record with the required actor, action, timestamp and outcome.

**Scenario 2: Record a relevant failed action.** **Given** an in-scope operation fails, **when** the system handles the failure, **then** it records the failure outcome where the audit policy requires it and logging can be done safely.

**Scenario 3: Exclude sensitive authentication values.** **Given** a user authenticates or performs an audited operation, **when** the system writes the log record, **then** passwords and prohibited secrets are not included.

**Scenario 4: Restrict audit-log access.** **Given** a user without permission to review audit records, **when** they attempt to access audit-log information, **then** the backend denies access.

**Verification:** Successful actions, relevant failures, sensitive-data exclusion and audit-log access control.

## 8. Verification and Testing

### 8.1 Approach

HIVE is verified through unit tests (validation, normalization, detection rules), API tests (request handling, authentication, authorization, error responses), integration tests (database persistence and component interaction), frontend tests (dashboard states and interactions), non-functional tests (response time, recovery) and, where automation is impractical, manual verification with recorded steps and evidence. Tests are repeatable, use controlled synthetic data, and do not depend on unauthorized external systems or real production data.

### 8.2 Test Categories

Results are classified as **prototype tests** (a limited component or preliminary implementation), **requirement acceptance tests** (tied to a specific user story), **non-functional tests** (quality attributes such as response time) or **manual verification**. Prototype tests do not establish that a requirement is satisfied. For example, passing JSON-validation or handler-recovery tests says nothing about authentication, authorization, persistence, alert generation or dashboard behavior.

### 8.3 Current Test Results

The team reports six passing Go prototype tests, covering malformed JSON rejection, missing required fields, valid event acceptance, unsupported HTTP methods, handler recovery after invalid requests, and a preliminary handler response-time measurement. They exercise the event handler only. They partly support FR-04, NFR-02 and NFR-04 and give an early indication for NFR-03, but do not replace the requirement-level procedures defined in Sections 5 to 7.

## 9. Security and Data Handling

HIVE is a cybersecurity monitoring project and follows these rules.

### 9.1 Authentication and Secrets

- Passwords are not stored in plaintext.
- Authentication secrets are not committed to the repository and are supplied through documented environment variables or another approved configuration mechanism.
- Error messages do not disclose passwords, tokens or other sensitive authentication data.

### 9.2 Authorization

- Backend operations enforce their required permissions; frontend restrictions are never a substitute for backend authorization.
- Access to audit records and administrative functionality follows the documented permission model.

### 9.3 Input Validation

- The backend validates request structure and required fields, and invalid input does not terminate the service.
- Unsupported or malformed event data is handled according to a documented policy.
- Test data is synthetic or otherwise approved for academic use.

### 9.4 Audit Logs

- Audit records contain only the information needed for accountability and investigation.
- Passwords and prohibited authentication secrets are not logged, and audit-log access is controlled.
- Limitations in audit completeness or tamper resistance are documented (see Section 10.3).

### 9.5 Safe Testing

Testing is limited to systems, honeypots, environments and data the team is authorized to use. The project does not claim production security certification; its security properties are evaluated against the implemented controls and the evidence collected.

## 10. Design Decisions and Known Limitations

### 10.1 Decisions Made

| Area | Decision |
|---|---|
| Backend language and API | Go backend exposing a REST API |
| Persistent storage | PostgreSQL |
| Frontend | React web interface |
| Initial integrations | SSH and HTTP/web honeypots |
| Elasticsearch | Optional; not part of the required architecture |
| Test data | Synthetic or otherwise approved non-sensitive data only |

### 10.2 Decisions Not Yet Finalized

The following design choices are not yet fixed. Each is shown with the constraints this specification already places on it.

| Area | Constraints already defined | Status |
|---|---|---|
| Authentication mechanism and session/token behavior | Passwords not stored in plaintext; 401 for missing or invalid credentials (NFR-01); disabled accounts denied (US-01) | Not finalized |
| Roles and permissions | Backend-enforced; 403 for insufficient permission (NFR-01, NFR-06); audit-log access restricted (US-08) | Role-permission matrix not finalized |
| Event transport and source authentication | Only registered, supported sources accepted; invalid source information rejected (FR-04) | Not finalized |
| Common event schema | Must define required and optional fields, types, timestamp representation and validation rules (NFR-08) | Field definitions not finalized |
| Mandatory detection rules | Each rule needs documented conditions and a verification test (FR-06) | Initial rule set not finalized |
| Audit scope | Records contain actor, action, timestamp, outcome, target where applicable (FR-08) | Audited-action list and retention not finalized |
| Performance test conditions | 100 valid requests, 95% under 500 ms, environment documented (NFR-03) | Concurrency level not finalized |
| Integration test coverage | Persistence and component interaction covered (Section 8.1) | Minimum set not finalized |

### 10.3 Known Limitations

- The performance result in NFR-03 is a local academic benchmark and not a production scalability guarantee.
- HIVE does not guarantee detection of every attack and does not replace a SIEM or SOC platform.
- Tamper resistance of audit logs is not claimed; any limits on audit completeness are documented with the audit scope.
- Only the SSH and HTTP/web event formats are targeted initially; other formats are unsupported.

## 11. Completion Criteria

The initial deliverable is considered complete when all eight Must functional requirements are implemented and covered by automated success and failure tests; NFR-01 to NFR-10 have recorded verification results; the ingestion performance result states its environment and measurement method; dashboard loading, empty and error states are verified; the setup instructions have been followed in a clean environment; security testing used only authorized environments and non-sensitive data; and every user story is maintained in its own Markdown file alongside a committed use case diagram, work breakdown structure, PERT dependency network and Gantt chart. Any outstanding exception is documented and approved. Test failures are investigated, not concealed or marked as passing.
